# Разбор решения задач:

## 1. Что такое API Gateway и зачем он нужен

**API Gateway** - это единая точка входа для клиентских запросов в микросервисную архитектуру, которая скрывает внутреннюю топологию сервисов и берёт на себя сквозные задачи: маршрутизацию, аутентификацию, TLS-терминацию, rate limiting и логирование. Без него каждый клиент был бы вынужден знать адреса всех сервисов и дублировать логику безопасности в каждом из них.

## <mark style="background:#b1ffff">Выбор решения: Kong Gateway</mark>.
**Kong** cоздан на основе Nginx (использующий OpenResty под капотом). Его сильная сторона - экосистема плагинов.Cуществует в свободном и коммерческом варианте, может быть запущен как самостоятельное приложение (например, через docker-контейнер), либо установлен в Kubernetes (в этом случае он представляется как специализированный Ingress-контроллер). Для управления Kong можно использовать как запросы к API, так и веб-интерфейсы Kong Manager или [Konga](https://hub.docker.com/r/pantsel/konga). Многие расширения предустановлены в официальном контейнере, но они также могут быть найдены в [Kong Plugin Hub](https://docs.konghq.com/hub/). (https://habr.com/ru/companies/otus/articles/669342/)

## Обоснование 
1. **Маршрутизация на основе конфигурации.** Kong использует декларативную модель «Service - Route»: маршруты описываются в YAML и применяются через Admin API или в DB-less режиме напрямую из файла. Конфигурация хранится в Git и применяется через CI/CD.
2. **Проверка аутентификации.** Встроенные плагины key-auth, JWT, OAuth2 и LDAP-auth позволяют валидировать учётные данные на уровне шлюза, не внедряя код аутентификации в каждый микросервис. Политики применяются точечно - отдельным сервисам и маршрутам.
3. **Терминация HTTPS.** Kong терминирует TLS с поддержкой SNI и нескольких сертификатов; в Kubernetes интегрируется с cert-manager для автоматического выпуска и ротации сертификатов Let's Encrypt.
## Дополнительные аргументы 

- **Отказоустойчивость:** кластер из нескольких нод Kong с общей PostgreSQL либо  stateless DB-less режим. Оба варианта укладываются в стандартные схемы HA.
- **Масштабируемость:** stateless-ноды шлюза горизонтально масштабируются под ростом нагрузки без изменения архитектуры.
- **Наблюдаемость:** плагины Prometheus и логирования дают метрики и трейсинг из коробки — критично для эксплуатации.
- **Оpen-source** и развёртывание в собственной инфраструктуре не требует обязательного лицензирования.
- **Почему не альтернативы:** Traefik проще в эксплуатации, но слабее по встроенным механизмам аутентификации; KrakenD быстрее, но имеет минимальную экосистему плагинов; Nginx требует программирования логики шлюза на Lua; Tyk функционально богат, но тянет больше инфраструктурных зависимостей (Redis, СУБД, dashboard). Kong - оптимальный баланс возможностей, зрелости и эксплуатационной сложности.

## Плагины для Kong

- Ограничение скорости (на потребителя, на маршрут, на IP)
- JWT / OAuth2/Аутентификация ключа API
- Преобразование запроса/ответа
- Кэширование
- Вход в Datadog, Splunk, конечные точки HTTP
- Ограничение IP
- Обнаружение ботов
- И 100+ плагинов сообщества
  
## Недостатки Конга

- **Сложность конфигурации** - KongIngress, KongPlugin, KongConsumer, HTTPRoute - есть много CRD, которые нужно изучить
- **Использование ресурсов** - тяжелее, чем Traefik или ванильный Nginx
- **Возможности Enterprise - некоторые плагины (OIDC, интеграция с Vault, расширенная аналитика) предназначены только для Kong Enterprise
- **Поддержка API шлюза** - есть, но исторически полагался на свои собственные CRD

### Вместе с тем, под требования задания (конфигурационная маршрутизация, проверка аутентификации и HTTPS-терминация) также подходят **Nginx и Traefik**

**Nginx** даёт максимальный контроль через конфигурацию, **Traefik** делает акцент на автоматическом service discovery, а **Kong** на API-функциях и плагинах. Это разные уровни сложности под разные требования. 
- **Целесообразно использовать Traefik,** если заказчик - стартап или небольшая команда, нужна быстрая настройка или используется смешанные среды Docker + Kubernetes.
   
   - **Целесообразно использовать Nginx Ingress**, если нужна проверенная стабильность в масштабе, команда знает Nginx или есть простые требования к маршрутизации.
   
   - **Целесообразно использовать Kong,** если заказчик создает платформу с API, ориентированными на разработчиков, необходимо управление ключами API и ограничение скорости для каждого клиента или нужна экосистема плагинов вместо написания собственного промежуточного программного обеспечения.

## 2: Брокер сообщений
**Брокер сообщений** - это отдельный компонент между микросервисами: один сервис отправляет в него сообщение, а другой забирает и обрабатывает позднее. Это позволяет сервисам работать асинхронно и не зависеть от доступности друг друга в момент отправки.
Пример: сервис заказов публикует событие `order.created`; сервисы оплаты, уведомлений и склада получают его и выполняют собственную обработку. Сервис заказов не ждёт, пока каждый из них завершит работу.
Для сравнения  продуктов данного класса возьмем:
- **RabbitMQ** - классический AMQP-брокер с очередями, маршрутизацией и гибкими правами. Спроектирован как брокер очередей: сервис публикует сообщение, consumer получает его, подтверждает обработку (`ack`), после чего сообщение удаляется. Обычно проще в эксплуатации и понятнее в рамках базовой микросервисной архитектуры. Хорошо подходит для сценария «передать задачу из одного микросервиса другому, обеспечить сохранность и права доступа».
- **Apache Kafka** - распределённая платформа потоковой передачи событий с высокой пропускной способностью и хранением событий на диске. Сообщения хранятся по политике retention, а consumer сам отслеживает, какую позицию журнала он уже обработал. Хорош для очень больших потоков событий, повторного чтения истории, аналитики и event streaming. Может быть лучшим кандидатом, но он заметно сложнее в администрировании.
- **NATS JetStream** - лёгкий брокер, где JetStream добавляет хранение сообщений на диске и кластеризацию.
- **Redis Streams** - быстрый вариант для потоков, но имеет меньше специализированных возможностей очередей и требует внимательной настройки persistence/HA.

Главная разница между двумя наиболее популярными решениями RabbitMQ и Kafka: 
- RabbitMQ хранит сообщение, пока его успешно не обработает потребитель; 
- Kafka хранит события некоторое время независимо от того, кто и когда их прочитал.
### Представим сервис интернет-магазина:
Сервис заказов создал заказ №1001. После этого нужно:
- списать товар на складе;
- отправить письмо клиенту
- передать данные в аналитику.

#### RabbitMQ удобнее представить как **очередь заданий для исполнителей**.

Сервис заказов ➡️ «Отправляет письмо по заказу №1001» ➡️ Очередь RabbitMQ  ➡️ Сервис уведомлений ➡️ Обработал письмо успешно - ACK ➡️ RabbitMQ удаляет сообщение`

Здесь сообщение имеет практический смысл: **«сделай конкретную работу»**.

1. Сервис уведомлений получает задание.
2. Он отправляет письмо.
3. Только после успеха он отправляет брокеру подтверждение — `ACK`.
4. RabbitMQ удаляет сообщение из очереди.

Если сервис упал до `ACK`, RabbitMQ считает, что задание не завершено, и может отдать его другому экземпляру сервиса. Документация RabbitMQ рекомендует ручное подтверждение (`manual acknowledgement`) именно для того, чтобы необработанное сообщение вернулось в очередь.
## Ключевая мысль
В RabbitMQ сообщение обычно **исчезает после успешной обработки**. Это похоже на бумажную заявку: исполнитель взял её, сделал работу, отметил выполнение - заявка убирается.

## Kafka: сохраняет факт события

Kafka удобнее представить как **журнал событий**, в который нельзя исправлять или вырывать уже записанные страницы.

Сервис заказов ➡️ «Заказ №1001 создан»  ➡️ Kafka topic: orders  ➡️ Склад читает событие 
														  ➡️ Уведомления читают событие 
														  ➡️ Аналитика читает событие`

Сообщение здесь имеет другой смысл: **«произошёл факт»**.

Kafka записывает событие в topic на диск и хранит его по настроенной политике времени или размера. То есть даже когда склад, уведомления и аналитика прочитали событие, запись остаётся в Kafka, пока не истечёт период хранения. Kafka описывает это как долговременное и надёжное хранение потоков событий в topics.

### У каждого события в Kafka есть порядковый номер - **offset**:

Topic orders:   offset 0: Заказ №999 создан 
		    offset 1: Заказ №1000 создан 
		    offset 2: Заказ №1001 создан 
		    offset 3: Заказ №1002 создан`

Каждый потребитель сам хранит отметку, до какого сообщения он дочитал:
- Склад:                прочитал до offset 2
- Уведомления:   прочитали до offset 1 
- Аналитика:       прочитала до offset 2`

Поэтому один сервис может прочитать событие сразу, другой через час, а третий может позже перечитать всю историю за неделю. Само событие из Kafka не удаляется потому, что его прочитал один сервис. Kafka организует события в долговечно хранимые topics.

## Кратко:

| Вопрос                               | RabbitMQ                                        | Kafka                                                           |
| ------------------------------------ | ----------------------------------------------- | --------------------------------------------------------------- |
| Смысл сообщения                      | «Выполни задачу»                                | «Произошло событие»                                             |
| После успешной обработки             | Обычно удаляется из очереди после `ACK`         | Остаётся в topic до окончания retention                         |
| Кто управляет фактом обработки       | Брокер ждёт `ACK` от consumer                   | Consumer сохраняет свой offset                                  |
| Повторно обработать старые сообщения | Возможно, но это не основная модель             | Естественный штатный сценарий                                   |
| Хороший пример                       | Отправить email, создать PDF, обработать платёж | История заказов, аналитика, аудит, интеграция нескольких систем |

**RabbitMQ** поддерживает ручные подтверждения обработки и повторную доставку необработанных сообщений; 
**Kafka** ориентирован на публикацию, чтение и долговременное хранение потоков событий.kafka.

На практике **RabbitMQ тоже может доставлять одно сообщение нескольким сервисам** через механизм exchange и несколько очередей. Но для каждого сервиса создаётся своя очередь, и каждое сообщение из этой очереди будет удалено после его `ACK`.

**Kafka**, наоборот, изначально хранит одно событие в общем журнале, а разные группы потребителей читают его независимо. Поэтому Kafka особенно удобна, если сегодня событие слушают склад и уведомления, а через месяц появляется новый сервис аналитики, которому нужно прочитать историю старых заказов.

## Вывод: 
Для системы на основе микросервисной архитектуры предлагаю использовать **RabbitMQ**. Он лучше всего соответствует заданным требованиям, поскольку сочетает надёжную доставку сообщений, дисковое хранение, кластеризацию, разграничение доступа и сравнительно простую эксплуатацию.

- **RabbitMQ** поддерживает durable queues и кластеризацию; quorum queues предназначены для реплицируемых, согласованных очередей. 
- **Kafka** представляет собой распределённый журнал событий, в котором записи сохраняются и не удаляются непосредственно после чтения consumer. 
- **JetStream** является встроенным в NATS уровнем persistence и streaming.

**RabbitMQ в кластере из трёх узлов с quorum queues** обеспечивает отказоустойчивость: сообщения реплицируются между узлами, и отказ одного узла не приведет к их потере.

Требование хранения сообщений на диске выполняется с помощью durable/quorum queues и публикации persistent messages. При перезапуске узла не подтверждённые consumer сообщения сохраняются и могут быть повторно доставлены.

**RabbitMQ** обеспечивает высокую скорость, достаточную для большинства задач взаимодействия микросервисов: фоновой обработки, отправки уведомлений, работы с заказами, интеграции с платёжными и складскими сервисами. **Kafka** может дать более высокую пропускную способность, но его преимущество проявляется прежде всего при очень больших потоках событий, аналитике и необходимости повторно читать историю сообщений.

**RabbitMQ** не ограничивает формат полезной нагрузки: сервисы могут передавать JSON, XML, Protobuf или Avro. При этом формат и версия сообщения должны быть согласованы на уровне контрактов producer и consumer; сам брокер доставляет payload, а не интерпретирует бизнес-структуру данных.

Для разграничения доступа **RabbitMQ** поддерживает пользователей, virtual hosts и права на конфигурирование, публикацию и чтение очередей. Это позволяет изолировать потоки: например, сервис уведомлений получает доступ только к своей очереди, а сервис оплаты - только к связанным с оплатой exchanges и queues.

**RabbitMQ** проще в эксплуатации, чем Kafka, для базового сценария очередей задач: доступны web management UI, CLI-инструменты и метрики; модель exchange - queue - consumer наглядна для разработки и сопровождения. **Kafka** следует выбрать, если главным требованием станут очень высокая пропускная способность, хранение событий как журнала и их повторное чтение многими потребителями.
## Итоговое обоснование

RabbitMQ выбран как оптимальный брокер сообщений для микросервисной системы, поскольку он:
- поддерживает кластеризацию и репликацию сообщений через quorum queues;
- обеспечивает дисковое хранение сообщений до успешной обработки;
- имеет достаточную производительность для типового межсервисного взаимодействия;
- передаёт сообщения в различных форматах;
- предоставляет гибкое разграничение прав доступа;
- проще в администрировании и сопровождении, чем Kafka, если не требуется потоковая аналитика и длительное хранение истории событий.

# Разбор решения задания: 

- Клонировал учебный репозиторий git clone https://github.com/netology-code/devkub-homeworks.git
- Убрал лишнее и подключил к нему удаленный репозиторий https://github.com/ArturP1rozhkov/microservises
- В репозитории заменил содержимое файла `/gateway/nginx.conf` на это:
```yaml
events {}

http {
    server {
        listen 8080;
        server_name _;

        location = /token {
            proxy_pass http://security:3000/v1/token;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }

        location = /auth {
            internal;

            proxy_pass http://security:3000/v1/token/validation;
            proxy_pass_request_body off;

            proxy_set_header Content-Length "";
            proxy_set_header Authorization $http_authorization;
        }

        location = /upload {
            auth_request /auth;

            proxy_pass http://uploader:3000/v1/upload;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header Authorization $http_authorization;
        }

        location /images/ {
            auth_request /auth;

            proxy_pass http://storage:9000/data/;
            proxy_set_header Host storage:9000;
            proxy_set_header Authorization "";
        }
    }
}
```

`auth_request /auth` запускает внутренний подзапрос к `security` до передачи запроса в `uploader` или MinIO. Ответ `2xx` разрешает исходный запрос; `401` или `403` возвращается клиенту, а `internal` запрещает обратиться к `/auth` напрямую снаружи.n
## Комментарии к содержимому
- `location = /token` - внешний endpoint логина; Nginx меняет только маршрут с `/token` на `/v1/token`.
- `location = /auth` - служебный маршрут только для Nginx; тело файла туда не отправляется, передаётся `Authorization`.
- `location = /upload` - защищённая загрузка: сначала валидация JWT, затем передача исходного файла в `uploader`.
- `location /images/` - защищённое получение файла: запрос к `/images/photo.jpg` перенаправляется в `storage:9000/data/photo.jpg`.
- `proxy_pass http://storage:9000/data/` с завершающим `/` корректно заменяет префикс `/images/` на `/data/`.


Исправления ошибок версий:
В файле `docker-compose.yaml` d сервисе `createbuckets` заменил блок `entrypoint` на это
``` yaml
    entrypoint: >
      /bin/sh -c "
      /usr/bin/mc alias set storage http://storage:9000 ${Storage_AccessKey:-STORAGE_ACCESS_KEY} ${Storage_Secret:-STORAGE_SECRET_KEY} &&
      /usr/bin/mc mb --ignore-existing storage/${Storage_Bucket:-data} &&
      /usr/bin/mc anonymous set download storage/${Storage_Bucket:-data} &&
      exit 0;
      "
```
В актуальном образе `minio/mc` команды `config` больше нет. Её заменили на  `mc alias set` (https://github.com/minio/minio/issues/21327). В итоге:
- `mc config host add` стал  `mc alias set storage ...` - создаёт алиас `storage` для обращения к MinIO.
- `mc policy set download` стал `mc anonymous set download` - актуальная команда, разрешающая анонимное чтение объектов в bucket.
- `${Storage_AccessKey:-...}` и `${Storage_Secret:-...}`  сохранены в исходном виде. Compose подставит значения из `.env`.

В файл `requirements.txt` добавил строки:
- `Jinja2==3.0.3`. С этой версией jinja старый Flask совместим. Jinja2 3.0.3 - последняя ветка, где `escape` ещё экспортировался из `jinja2`. (https://stackoverflow.com/questions/71718167/importerror-cannot-import-name-escape-from-jinja2/76158079)
- `itsdangerous==2.0.1`. Это следующая несовместимость того же старого Flask 1.x: Flask пытается импортировать `json` из `itsdangerous`, но в новых версиях `itsdangerous` этого API больше нет. Для Flask 1.1.x нужно зафиксировать `itsdangerous==2.0.1` (https://stackoverflow.com/questions/71189819/importerror-cannot-import-name-json-from-itsdangerous/71213267)
- `Werkzeug==2.0.3`. Flask 1.x несовместим с новым Werkzeug: класс `BaseResponse` был убран из `werkzeug.wrappers` начиная с версии 2.1. Для этой версии Flask нужно закрепить `Werkzeug==2.0.3`. (https://github.com/SeldonIO/seldon-core/issues/4017)
